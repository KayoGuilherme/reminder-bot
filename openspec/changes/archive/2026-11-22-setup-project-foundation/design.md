# Design

## Context

See proposal.md for motivation. Observed current state of the repository:

- Maven project (wrapper present) generated by Spring Initializr: parent `spring-boot-starter-parent` **4.2.0**, `java.version` 21, `groupId com.telegram.reminder`, `artifactId bot`.
- Already declared: `data-jpa`, `starter-flyway`, `flyway-database-postgresql`, `validation`, `webmvc`, PostgreSQL driver, Lombok, devtools, and matching `*-test` starters. **Not** declared: Actuator, Testcontainers.
- Code: only `com.telegram.reminder.bot.BotApplication` and an empty `contextLoads` test. `src/main/resources/application.yaml` holds only `spring.application.name`. No migrations. `openspec/specs/` is empty.
- Single instance only; one allowed Telegram user.

## Goals / Non-Goals

**Goals:**
- Fail-fast, typed configuration; UTC everywhere internally; Flyway-owned schema.
- One command (`docker compose up --build`) yields a healthy stack; CI proves a clean clone builds and the schema migrates on real PostgreSQL.

**Non-Goals:**
- No entities, repositories, Telegram/STT/LLM code, scheduler, or REST API.
- No horizontal-scaling concerns (leader election, shared locks, distributed cache, broker, Kubernetes manifests).
- No automatic deployment, no image signing/SBOM, no multi-arch publishing beyond what is trivial (see Risks).

## Decisions

1. **Keep Spring Boot 4.2.0 (the existing parent) instead of downgrading to 3.x.**
   The request says "Spring Boot 3.x", but the repo already uses 4.x starters (`spring-boot-starter-flyway`, `*-test` starters) that do not exist in 3.x. Downgrading is churn with no benefit for a greenfield foundation. *Alternative*: pin 3.5.x and rewrite the pom. Flagged as an assumption below; trivial to reverse before apply.

2. **Rename package and groupId to `com.kayo.reminder`.** The user explicitly specified it. Move `BotApplication` (kept as the main class) and its test to `com.kayo.reminder`; set `groupId` to `com.kayo.reminder`. Hexagonal packages `domain`, `application.port.in`, `application.port.out`, `application.service`, `infrastructure`, `config` are created with a `package-info.java` only where a package would otherwise be empty (git does not track empty dirs). *Alternative*: keep `com.telegram.reminder.bot` – rejected as it contradicts the request.

3. **Config files use `application.yaml` (the existing extension)**, plus `application-local.yaml` and `application-prod.yaml`. The request wrote `.yml`; both are equivalent to Spring, and mixing extensions would be confusing.

4. **Typed properties: one `AppProperties` record bound to prefix `app`, `@Validated`, registered with `@ConfigurationPropertiesScan`/`@EnableConfigurationProperties`.**
   Nested records: `telegram(botToken @NotBlank, allowedUserId @NotNull Long)`, `groq(apiKey @NotBlank)`, `gemini(apiKey @NotBlank)`, `timezone ZoneId @NotNull` (Spring converts the string; an invalid id fails binding). `application.yaml` maps `app.telegram.bot-token: ${TELEGRAM_BOT_TOKEN}` etc. with **no default** for secrets so an absent variable fails placeholder resolution or validation with a clear message; `app.timezone: ${APP_TIMEZONE:America/Fortaleza}`. Blank-but-present values (e.g. `TELEGRAM_BOT_TOKEN=` in a half-filled `.env`) are caught by `@NotBlank`. `toString` of secret-bearing records is overridden/masked so accidental logging cannot leak.
   *Alternative*: `@Value` injection – rejected: no grouped validation, weaker error messages.

5. **UTC handling.** `Clock.systemUTC()` bean in `config.ClockConfig`. JVM: `-Duser.timezone=UTC` in the container `JAVA_OPTS`, and `spring.jpa.properties.hibernate.jdbc.time_zone: UTC` plus `TimeZone.setDefault` avoided in code (kept declarative). Domain time is `Instant`; conversion to `app.timezone` happens only at presentation edges (future changes).

6. **Schema.** `V1__create_tasks_table.sql` exactly as specified; CHECK constraints named (`tasks_urgency_check`, `tasks_status_check`); index `idx_tasks_status_deadline` on `(status, deadline_at)`. UUIDs are generated by the application (no DB default, so no `pgcrypto` dependency). `updated_at` is maintained by application code in a later change (no trigger now – keeps the migration minimal). `spring.jpa.hibernate.ddl-auto: validate`; with zero entities this validates nothing yet, which is intended. `spring.jpa.open-in-view: false`.

7. **Actuator.** Add `spring-boot-starter-actuator`. `management.endpoints.web.exposure.include: health,info`; `management.endpoint.health.probes.enabled: true`; `show-details: never`. The default DB health indicator makes `/actuator/health` depend on PostgreSQL, which is what we want for a single instance. Since webmvc is present the app listens on `8080`; it is **not** published to the host in the base compose file (the bot uses Telegram long polling later, so no inbound traffic is needed). The override publishes it on `127.0.0.1:8080` for local checks.

8. **Logging.** Root `INFO`; `com.kayo.reminder` `INFO` (`DEBUG` only in `local`); no request/SQL logging in prod (`spring.jpa.show-sql: false`). Secrets are never logged by our code; masked `toString` (decision 4) covers accidents. Note that Telegram/Groq HTTP client debug logging (future) must stay off in prod.

9. **Dockerfile.** Stage 1 `eclipse-temurin:21-jdk` (Debian, glibc): copy `.mvn`, `mvnw`, `pom.xml` first and run `./mvnw -B dependency:go-offline` for layer caching, then copy `src` and `./mvnw -B -DskipTests package`; extract Spring Boot layers (`java -Djarmode=tools extract --layers`, Boot 3.3+/4) to get cache-friendly layers. Stage 2 `eclipse-temurin:21-jre-alpine` (slim JRE): create user `app` (non-root), copy layers, `ENV JAVA_OPTS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError -Duser.timezone=UTC"`, `ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS org.springframework.boot.loader.launch.JarLauncher"]`, `HEALTHCHECK` using busybox `wget -qO- http://localhost:8080/actuator/health/readiness` with start-period for Flyway. Tests are skipped in the image build (CI runs them) to avoid needing Docker-in-Docker for Testcontainers inside `docker build`. *Alternative*: simple fat jar – layered extraction costs a few lines and speeds rebuilds/pulls on a Raspberry Pi, so kept. Alpine is used for the small healthcheck-capable runtime; `eclipse-temurin` publishes `arm64` variants for Pi.

10. **Compose.** `docker-compose.yml`: `db` = `postgres:16-alpine` (pinned major), named volume `pgdata`, healthcheck `pg_isready -U $DB_USER -d <db>`, `POSTGRES_*` from `.env`; `app` = `build: .` and `image: ghcr.io/${GITHUB_REPOSITORY_OWNER:-OWNER}/...` tag so the same file can pull the published image (`docker compose pull`), `env_file: .env`, `depends_on: db: condition: service_healthy`, both `restart: unless-stopped`. `DB_URL` in `.env.example` points at host `db` (`jdbc:postgresql://db:5432/reminder`). `docker-compose.override.yml` (auto-loaded by `docker compose`) adds `127.0.0.1:5432:5432` for db, `127.0.0.1:8080:8080` for app and `SPRING_PROFILES_ACTIVE=local`. Server/Pi usage: `docker compose -f docker-compose.yml up -d` (explicitly skipping the override), documented in README. Production default profile in the base file is `prod`.

11. **Tests.** One smoke test: `@SpringBootTest` with a Testcontainers `PostgreSQLContainer` via `@ServiceConnection` (Boot 4 `spring-boot-testcontainers`), plus `app.*` test properties; assertions: context loads and `flyway_schema_history` contains version 1 as success and `tasks` has the expected columns/index (cheap `JdbcTemplate` queries against `information_schema`/`pg_indexes`). Small unit tests for `AppProperties` validation (missing token, bad timezone) using `ApplicationContextRunner` cover the fail-fast acceptance criterion without a database. The devtools dependency stays `runtime/optional` and is excluded from the repackaged jar by default.
    *Alternative*: CI Postgres service container – rejected because Testcontainers makes `./mvnw verify` behave identically locally and in CI.

12. **CI/CD.** `ci.yml`: triggers `pull_request` and `push` to `main`; `actions/checkout`, `actions/setup-java` (temurin 21, `cache: maven`), `./mvnw -B verify`. GitHub-hosted Ubuntu runners include Docker, so Testcontainers works with no service container and no secrets. `docker.yml`: trigger `workflow_run` of `ci` (`types: [completed]`, `branches: [main]`) with job-level `if: github.event.workflow_run.conclusion == 'success' && github.event.workflow_run.event == 'push'`; checkout the `workflow_run.head_sha`; `docker/login-action` to `ghcr.io` with `GITHUB_TOKEN` (`permissions: contents: read, packages: write`); `docker/metadata-action` + `docker/build-push-action` pushing tags `sha-<full or short sha>` and `latest`. Image name lowercased from `github.repository`. Optional: `docker/setup-buildx-action` with GHA layer cache.

## Risks / Trade-offs

- **Boot 4.x vs requested 3.x** → documented assumption; reversible by changing the parent and starter names before apply.
- **Testcontainers API drift on Boot 4 (Testcontainers 2.x artifact/class names)** → resolve exact coordinates during apply from the Boot 4.2 BOM; if the BOM manages them, no versions are pinned.
- **Healthcheck depends on `wget` in Alpine/busybox** → verified during apply by running the container and checking `docker ps` health; fall back to a `curl` install or a tiny Java-based check if absent.
- **`workflow_run` runs workflow files from the default branch and has a slightly delayed trigger** → acceptable for a single repo; alternative (`needs:` via a reusable workflow) is more complex for little gain.
- **First `docker` run requires the GHCR package to be created/linked to the repo** → `GITHUB_TOKEN` with `packages: write` creates it on first push; visibility defaults to private, README notes how to make it public or `docker login ghcr.io` on the host.
- **Image is built for the runner architecture (amd64) only** → Raspberry Pi (arm64) users build locally with `docker compose up --build` or we add `platforms: linux/amd64,linux/arm64` (QEMU) later; deferred to keep CI fast.
- **Mandatory secrets at startup block running the app with feature subsets** → intentional for fail-fast; developers use dummy values from `.env.example` locally.
- **Rename of package/groupId touches the generated files** → small, mechanical, done in the first task group with the compile/test as verification.

## Migration Plan

1. Land the change; no existing deployment or data exists, so there is no data migration.
2. Operators copy `.env.example` to `.env`, fill values, and run compose. Rollback = previous image tag (`sha-…`) plus the unchanged Postgres volume; V1 is additive only and never rewritten (future schema changes are new `V<n>` files).
